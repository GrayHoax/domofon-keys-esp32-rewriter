# RW1990 / DS1990A программатор на ESP32-C3 / C6

Прошивка для ESP32-C3 / ESP32-C6, превращающая плату в сетевой программатор домофонных
ключей iButton. Устройство читает ключи DS1990A (и совместимые), записывает
заготовки RW1990.1 / RW1990.2 / TM01A / TM01C и проверяет их работоспособность. Управление —
через веб-интерфейс: по домашней Wi-Fi сети или через собственную точку доступа
устройства, если сеть недоступна или ещё не настроена.

## Возможности

- **Чтение** ROM-кода ключа (64 бита: семейство, серийный номер, CRC-8) с
  автоматическим обнаружением приложенного ключа.
- **Запись** заготовок RW1990.1 (команда `0xD1`, инверсные данные),
  RW1990.2 (команда `0x1D`, прямые данные) и TM01A/TM01C в режиме Dallas
  (команды `0xC1`/`0xC5`, собственные тайминги) с обязательной проверкой
  чтением после записи.
- **Проверка ключа**: серия повторных чтений (по умолчанию 10) с контролем
  CRC и сравнением с ожидаемым ID — выявляет плохой контакт, «полумёртвые»
  и неверно записанные ключи.
- **Wi-Fi**: подключение к сохранённой сети; при отсутствии настроек или
  недоступности сети устройство поднимает точку доступа `RW1990-XXXXXX` и
  периодически пытается переподключиться. Captive-portal DNS открывает
  страницу настройки автоматически.
- **Веб-интерфейс** (русский, адаптивный): считыватель, запись, проверка,
  журнал операций, настройка Wi-Fi (сканирование сетей, сохранение
  учётных данных, настройка собственной точки доступа), системная информация.
- **База ключей** в отдельном разделе флеша (~2.4 МБ): каждый корректно
  считанный ключ сохраняется автоматически, повторы отбрасываются. Названия
  до 120 символов (кириллица/латиница), поиск, запись любого ключа из базы
  на заготовку, экспорт в файл и импорт из файла с дополнением или полной
  заменой базы.
- **REST API** (JSON) для интеграции и автоматизации.
- **mDNS**: интерфейс доступен как `http://rw1990.local`.
- **Статусный светодиод** (RGB на плате): состояние сети и результат
  операций. Поддерживаются дискретный RGB на трёх GPIO (NodeMCU
  ESP-C3-12F-Kit) и адресуемый WS2812 (ESP32-C6 DevKit).

## Аппаратная часть

Основная плата — **NodeMCU ESP-C3-12F-Kit** (модуль AI-Thinker ESP-C3-12F,
4 МБ flash, CH340 на USB). Также поддерживаются ESP32-C6-DevKitC-1 /
DevKitM-1 — дефолты пинов выбираются автоматически по целевому чипу.

| Сигнал | ESP-C3-12F-Kit | ESP32-C6 DevKit | Примечание |
|--------|----------------|-----------------|------------|
| 1-Wire DATA | **IO6** | GPIO4 | центральный контакт iButton |
| Подтяжка | IO6 ↔ 3V3, 2.2 кОм (до 4.7) | GPIO4 ↔ 3V3 | обязательна, внутренней недостаточно; других резисторов в линии не нужно |
| Вход АЦП (Cyfral/Metakom) | **GPIO0** (ADC1_CH0) ↔ DATA перемычкой — на гребёнке это пин `NC` между `EN` и `GND`, см. ниже | GPIO4 (= DATA, ADC1_CH4) | нужен только для чтения Cyfral/Metakom/финализированных TM01A |
| GND | GND | GND | обод (корпус) iButton |
| RGB LED | IO3 (R), IO4 (G), IO5 (B) | GPIO8 (WS2812) | на плате, ничего подключать не нужно |

```
 ESP-C3-12F-Kit
 ┌──────────┐            3V3 ──┬── резистор 2.2k ──┐
 │      3V3 ├────────────────┘                    │
 │      IO6 ├────────────────────────────────────┴──┬─ DATA (центр iButton)
 │    GPIO0 ├───────────────────────────────────────┘   (перемычка: АЦП слушает линию; на плате пин "NC" между EN и GND)
 │      GND ├───────────────────────────────────────── GND  (обод iButton)
 └──────────┘
```

> **Почему не один пин и где на самом деле IO0.** У IO6 нет АЦП, а
> свободные каналы ADC1 на этом ките — только GPIO0 и GPIO1 (IO2 —
> strapping, IO3/IO4 заняты светодиодом). По схеме ESP-C3-12F-Kit v1.0:
>
> - **GPIO1** нагружен на плате делителем «ADC»: header `ADC` → R9 4.7k →
>   GPIO1 → **R15 1 kΩ → GND**. Для 1-Wire непригоден (линия садится на
>   ~1 V), да и для АЦП бесполезен.
> - **GPIO0** свободен, на нём только подтяжка R17 4.7k к 3V3 — параллельно
>   нашей 2.2k получается ~1.5k, это нормально.
> - **Шелкография не совпадает со схемой**: пин, подписанный `IO0` (второй
>   сверху на правой гребёнке), в схеме заведён на GPIO1, а настоящий GPIO0
>   выведен на пин, подписанный **`NC` между `EN` и `GND`** (13-й сверху на
>   правой гребёнке). Проверка мультиметром: у настоящего GPIO0 без
>   подключений ≈3.3 V (через R17) и он не «садит» линию; у пина с
>   делителем ≈0 V. Прошивка при загрузке подтвердит: `line self-test:
>   GPIO6 reads HIGH, ADC idle ≈4095..4095`.
>
> Поэтому данные остаются на проверенном IO6, а АЦП подключается к линии
> перемычкой с настоящего GPIO0. Без перемычки всё, кроме Cyfral/Metakom,
> работает как прежде.

Всего один резистор — подтяжка DATA к 3V3. Он выполняет сразу три роли:
формирует высокий уровень для open-drain шины 1-Wire, питает ключ
(паразитное питание DS1990A/RW1990 и активное — Cyfral/Metakom) и служит
нагрузкой, на которой Cyfral/Metakom-ключ модулирует ток — именно это
падение напряжения видит АЦП. Никаких дополнительных резисторов в линии
(последовательных, делителя перед АЦП) не требуется: вход АЦП
высокоомный, а 3.3 V на пине — допустимый уровень для ESP32-C3. Номинал
2.2 кОм предпочтительнее 4.7: сильнее подтяжка — быстрее фронты для
TM01A и больше размах сигнала Cyfral/Metakom. Если хочется защитить пины
от статики с контактора, можно добавить 100 Ω последовательно между
платой и DATA — на работу это не влияет.

- IO6 свободен от strapping-функций и ничем на плате не занят. Не
  используйте IO1 (нагружен на плате), IO2/IO8/IO9 (strapping), IO18/IO19
  (светодиоды кита) и IO20/IO21 (UART0 USB-моста). Пины переназначаются в
  menuconfig: **1-Wire data GPIO** и **ADC GPIO sensing the key line**
  (`-1` отключает аналоговый вход).
- Линия данных работает в режиме open-drain от 3.3 V. Большинство ключей
  DS1990A/RW1990 стабильно работают от 3.3 V при подтяжке 2.2 кОм; если
  конкретная заготовка «не берётся», уменьшите номинал до 1 кОм. Подтяжка
  к 5 V недопустима без преобразователя уровня, если стоит перемычка на
  вход АЦП.
- RGB-светодиод на ESP-C3-12F-Kit включается высоким уровнем; если на вашей
  ревизии платы он с общим анодом, включите **RGB LED is active-low** в
  menuconfig. Там же можно переназначить любой пин: `idf.py menuconfig` →
  **RW1990 Programmer → Hardware**.

## Сборка и прошивка

Требуется [ESP-IDF](https://docs.espressif.com/projects/esp-idf/en/stable/esp32c6/get-started/index.html)
версии **6.0 или новее** (проект собран и проверен на v6.0.2; совместим с
5.3–5.4, где уже есть компоненты `esp_driver_gpio` / `esp_driver_rmt`).
Внешние компоненты (`espressif/mdns`, `espressif/led_strip`,
`espressif/cjson` — в IDF 6.0 cJSON вынесен из фреймворка в реестр)
подтягиваются менеджером компонентов автоматически при первой сборке.

```bash
idf.py set-target esp32c3        # или esp32c6 — пины и тип светодиода подставятся сами
idf.py menuconfig                # опционально: GPIO, пароль AP, таймауты
idf.py build
idf.py -p COM5 flash monitor
```

Проект также собирается CI (`.github/workflows/build.yml`) для обоих чипов
на нескольких версиях ESP-IDF; готовые бинарники доступны как артефакты
сборки.

## Первое включение

1. Устройство не имеет сохранённой сети и запускает точку доступа
   `RW1990-XXXXXX` (пароль по умолчанию `rw1990pass`, задаётся в menuconfig).
   Светодиод медленно мигает синим.
2. Подключитесь к ней телефоном или ноутбуком — страница настройки
   откроется автоматически (captive portal) или по адресу `http://192.168.4.1`.
3. На вкладке **Сеть** нажмите «Сканировать», выберите сеть, введите пароль
   и нажмите «Сохранить и подключиться».
4. После подключения светодиод загорится зелёным; в интерфейсе появится
   новый IP-адрес. Точка доступа выключится через 15 с (настраивается).
   Дальше интерфейс доступен по `http://rw1990.local` или по IP.

Если сохранённая сеть недоступна дольше 30 с — при включении или после
обрыва уже установленного соединения (например, роутер выключен) — устройство
поднимает свою точку доступа и раз в минуту в фоне пробует подключиться снова,
не мешая работе через AP. Как только сеть вернётся, точка доступа выключится
через 15 с. Таймауты настраиваются в `menuconfig` → RW1990 Programmer → Network.

### Индикация

| Светодиод | Состояние |
|---|---|
| Тусклый белый | загрузка |
| Медленно мигает синим | своя точка доступа, сеть не настроена |
| Синий с короткой красной вспышкой | своя точка доступа: настроенная сеть недоступна, идут фоновые попытки |
| Быстро мигает жёлтым | подключение к сети |
| Тусклый зелёный | подключено |
| Голубая вспышка | считан ключ |
| Две зелёные вспышки | запись/проверка успешна |
| Три красные вспышки | ошибка операции |

## Работа с ключами

**Чтение.** Приложите ключ к считывателю — ID появится на вкладке «Ключ»
автоматически (опрос каждые 300 мс). ID отображается в порядке передачи по
шине: `01 A1 B2 C3 D4 E5 F6 5C` — первый байт `01` это код семейства
DS1990A, последний — CRC-8. Кнопка «В поле записи» переносит прочитанный
ID в форму записи.

**Запись.** Введите ID (16 шестнадцатеричных цифр, разделители
необязательны), выберите тип заготовки и нажмите «Записать». Устройство
переходит в режим ожидания (до 30 с, на странице идёт обратный отсчёт):
приложите заготовку к контактам — как только она стабильно читается два
опроса подряд, начинается программирование. Ожидание можно отменить кнопкой
«Отмена». Если у ID неверная CRC (например, набран вручную), включите
«Автоисправление CRC». После программирования прошивка сразу читает ключ и
сравнивает с записанным; несовпадение возвращается как ошибка
`verify_failed` — обычно это означает, что выбран не тот тип заготовки,
попробуйте второй. Пока идёт ожидание, ID приложенной заготовки в базу не
сохраняется.

### Типы заготовок

| Тип в интерфейсе | Заготовки | Протокол записи |
|---|---|---|
| RW1990.1 | RW1990, RW1990.1, ТМ-08, ТМ-08v2 | флаг `0xD1` + импульс «0», ROM `0xD5` инверсно, флаг `0xD1` + импульс «1» |
| RW1990.2 | RW1990.2 | флаг `0x1D` + «1», ROM `0xD5` прямо, флаг `0x1D` + «0» |
| TM01A / TM01C | TM01, TM01A, TM01C (TM-01) | флаг `0xC1` + «1», ROM `0xC5` прямо, флаг `0xC1` + «0»; тайминги TM01 |

**Про TM01A.** Это универсальная заготовка (Dallas/Cyfral/Metakom) с
электрически «ленивым» 1-Wire: ей нужен более длинный reset (~740 мкс), она
отвечает presence-импульсом позже стандартных 15–60 мкс и раньше отпускает
линию в слоте чтения. Прошивка сначала опрашивает ключ стандартными
таймингами, а если никто не ответил — повторяет запрос таймингами TM01
(параметры взяты из открытой прошивки Flipper Zero). Если ключ прочитался
только вторым способом, под ID появится пометка «отвечает только на тайминги
TM01», а тип заготовки в форме записи переключится на TM01A/TM01C. Учтите:

- TM01A, уже финализированная под Cyfral или Metakom (команды `0xCA`/`0xCB`),
  перестаёт быть 1-Wire-устройством и *активно* выдаёт код на линию. Такой
  ключ читается через аналоговый вход (см. ниже), но перезаписать его этим
  устройством нельзя — нужен дубликатор с режимом стирания (TMD-5/TMD-6).
  Новую заготовку из упаковки пишите сразу в режиме Dallas.
- Заготовка после записи проверяется чтением; если проверка проходит, а
  домофон ключ не принимает, попробуйте другую подтяжку (2,2 кОм) — TM01A
  чувствительна к уровню на линии.
- Чем короче провода от платы до контактора, тем лучше: длинный reset и
  поздний presence у TM01 не любят ёмкости на линии.

### Чтение Cyfral и Metakom (в том числе TM01A в этих режимах)

Ключи Cyfral и Metakom не отвечают мастеру: получив питание через
подтяжку, они непрерывно передают код, модулируя ток на линии. Прошивка
ловит это АЦП: если 1-Wire-опрос никого не нашёл (или линия «дёргается»),
АЦП в режиме DMA записывает линию ~25 мс на 83 kS/s, сигнал режется по
порогу с гистерезисом на интервалы «высокий/низкий» и скармливается двум
декодерам, перенесённым из прошивки Flipper Zero:

- **Cyfral** — 16-битный код: стартовый ниббл `0001`, 8 нибблов с ровно
  одним нулём (2 бита каждый), стоп-ниббл `0001`; бит различается долей
  низкого уровня в периоде ~125 мкс.
- **Metakom** — 32-битный код: стартовые биты `010`, 4 байта с чётным
  паритетом, стоп `010`.

Результат виден на вкладке «Ключ» как `Cyfral XXXX` / `Metakom XXXXXXXX`
(биты в порядке приёма, старший первым; Flipper показывает те же байты в
обратном порядке). В базу 1-Wire ключей такие коды не попадают, запись их
на заготовки не реализована.

Чтобы это заработало, линию должен видеть пин ADC1: на ESP-C3-12F-Kit —
перемычка DATA↔IO0, на C6 GPIO4 сам является ADC1_CH4. При загрузке
прошивка пишет `line self-test: ... ADC idle N..M of 4095` — с перемычкой
и без ключа там должно быть ≈4095. Диагностика на новом железе —
`GET /api/key/analog`: возвращает размах сигнала в отсчётах АЦП (`swing`,
нужно ≥ 200 из 4095), число фронтов и средний период. Если `swing` мал —
ключ не модулирует линию при 3,3 В или подтяжка велика: попробуйте 2,2 кОм
или 1 кОм. Фронты есть, но `decoded=false` — пришлите вывод `/api/key/analog`,
это уровень порога/полярности.

**Проверка.** «Проверить ключ» выполняет 10 последовательных чтений и
требует, чтобы каждое прошло с верной CRC и совпало с ID в поле. Это
имитирует поведение домофона, который читает ключ несколько раз, и
позволяет отсеять ключи с нестабильным контактом.

Тайминги 1-Wire выполняются с запрещёнными прерываниями, поэтому Wi-Fi не
влияет на надёжность чтения. Presence-импульс ищется опросом линии в окне
250 мкс после reset, а не одной выборкой — так ловятся и стандартные ключи,
и «медленные» клоны. Запись занимает ≈1 с (64 бита × 10 мс).

## База ключей

Вкладка **База** показывает все сохранённые ключи (новые сверху). Ключ
попадает в базу в момент чтения, если CRC верна; уникальность обеспечивает
само хранилище — повторное прикладывание ничего не меняет. Для каждого ключа
можно задать название (до 120 символов), записать его на заготовку кнопкой
«Записать» (откроется диалог выбора типа RW1990) или удалить.

**Файл базы** — текстовый формат JSON Lines (`rw1990-keys.jsonl`, UTF-8):
по одному объекту на строку, строки с `#` и пустые игнорируются.

```
# RW1990 key database v1
{"id":"01A1B2C3D4E5F65C","name":"Подъезд 3, кв. 12"}
{"id":"0100112233445566","name":""}
```

Импорт в двух режимах: **Дополнить** — добавляются только отсутствующие
ключи (совпадения пропускаются, их количество показывается в отчёте);
**Заменить всю базу** — текущее содержимое стирается, для подтверждения
нужно ввести слово «ЗАМЕНИТЬ». Файл обрабатывается построчно, поэтому
размер базы ограничен только разделом флеша (2496 КБ, ~5–6 тыс. ключей с
названиями), а не оперативной памятью.

Хранилище — отдельный NVS-раздел `keydb` (см. `partitions.csv`), не
зависящий от настроек Wi-Fi: `idf.py erase-flash` его стирает,
перепрошивка приложения — нет.

## REST API

Все ответы — JSON с полем `ok`. Ошибки содержат `error` (код) и `message`.

| Метод | Путь | Описание |
|-------|------|----------|
| `GET` | `/api/status` | Прошивка, аптайм, состояние Wi-Fi и считывателя |
| `GET` | `/api/key` | Снимок состояния считывателя (`present`, `id`, `crc_ok`, `bus_shorted`, `tm01_timing`) |
| `POST` | `/api/key/read` | Немедленное чтение ключа (для Cyfral/Metakom — `proto` и `code`) |
| `GET` | `/api/key/analog` | Одна аналоговая выборка: `decoded`, `proto`, `code`, `signal{adc_min,adc_max,swing,edges,period_us}` |
| `POST` | `/api/key/write` | `{"id":"01A1B2C3D4E5F65C","variant":"rw1990v1"\|"rw1990v2"\|"tm01","fix_crc":false,"wait":true,"timeout_s":30}` — с `wait` отвечает `202` сразу и ждёт заготовку; без `wait` пишет немедленно |
| `GET` | `/api/key/write` | Состояние ожидающей записи: `job.state` (`idle`/`waiting`/`writing`/`done`), `remaining_s`, `result`, `message` |
| `DELETE` | `/api/key/write` | Отменить ожидание заготовки (или сбросить завершённую задачу) |
| `POST` | `/api/key/verify` | `{"id":"…","reads":10}` → `match`, `reads_ok`, `actual` |
| `GET` | `/api/wifi/scan` | Список сетей (`ssid`, `rssi`, `channel`, `auth`) |
| `POST` | `/api/wifi/sta` | `{"ssid":"…","password":"…"}` — сохранить и подключиться |
| `DELETE` | `/api/wifi/sta` | Забыть сеть, остаться в режиме AP |
| `POST` | `/api/wifi/ap` | `{"ssid":"…","password":"…"}` — параметры своей точки доступа |
| `GET` | `/api/keys` | Вся база: `stats` + массив `keys[{id,name,seq}]` |
| `POST` | `/api/keys` | `{"id":"…","name":"…","fix_crc":true}` — добавить вручную |
| `PUT` | `/api/keys/{id}` | `{"name":"…"}` — переименовать |
| `DELETE` | `/api/keys/{id}` | Удалить ключ |
| `DELETE` | `/api/keys` | Очистить базу |
| `GET` | `/api/keys/export` | Скачать базу (`.jsonl`) |
| `POST` | `/api/keys/import?mode=merge\|replace` | Тело — файл `.jsonl`; ответ: `total/added/skipped/invalid` |
| `POST` | `/api/system/reboot` | Перезагрузка |

Пример:

```bash
curl -X POST http://rw1990.local/api/key/write \
     -H 'Content-Type: application/json' \
     -d '{"id":"01 A1 B2 C3 D4 E5 F6 5C","variant":"rw1990v1","wait":true}'
# затем приложить заготовку и опрашивать
curl http://rw1990.local/api/key/write
```

## Структура проекта

```
main/                     точка входа, Kconfig проекта
components/
  onewire/                bit-bang мастер 1-Wire (сброс, слоты, импульсы программирования, CRC-8)
  ibutton/                чтение DS1990A, запись RW1990.1/.2/TM01, проверка, фоновый опрос
  activekey/              АЦП-захват линии и декодеры Cyfral/Metakom
  keydb/                  база ключей в отдельном NVS-разделе (уникальность, названия, итерация)
  wifi_manager/           STA ↔ AP-fallback автомат, NVS, сканирование, mDNS
  captive_dns/            DNS-ответчик для captive portal в режиме AP
  web_server/             HTTP-сервер, REST API (ключ, база, сеть), встроенный index.html
  status_led/             индикация: дискретный RGB (LEDC) или WS2812 (RMT)
partitions.csv            таблица разделов: приложение 1.5 МБ + раздел keydb 2.4 МБ
sdkconfig.defaults        базовые настройки (чип задаётся через idf.py set-target)
.github/workflows/        сборка в CI
```

Внешние зависимости объявлены в `idf_component.yml` тех компонентов,
которые их используют.
